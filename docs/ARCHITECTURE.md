# 系统架构说明书（零基础版）

> 目标读者：没有 Web 开发背景的人（导师、家人、跨专业的面试官、刚接手的新人）。
> 本文讲"系统由什么组成、数据怎么流动、为什么这样设计"，不深入代码细节——代码会持续演进，但骨架稳定。

---

## 1. 这个系统是做什么的

一句话：**自动把散落在各个政府网站上的财税政策收集起来，整理成一份排版好的 Word 日报**。

它解决的问题是：财税从业者每天要人工浏览多个政府网站找新政策，费时且容易漏。本系统用程序替代"浏览-筛选-整理-排版"这整套流程。

两种产出日报的方式：

| 方式 | 谁来决策 | 适合 |
|------|---------|------|
| 手动模式 | 人：勾选哪些政策进日报，一键导出 | 想精确控制内容的人 |
| Agent 模式 | AI 智能体：自主决定步骤，遇到不确定会**提问并等待人回答** | 想省事的人 |

## 2. 三大件：前端、后端、数据库

用餐厅做类比：

```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│   前端        │      │   后端        │      │   数据库      │
│  (餐厅店面)   │ ───→ │  (后厨)       │ ───→ │  (仓库)       │
│  Vue 网页     │      │  Django 服务  │      │  MySQL 表     │
└─────────────┘      └─────────────┘      └─────────────┘
   顾客看到的           处理逻辑的地方         存放数据的地方
   点菜界面             接单、做菜            食材、账本
```

**前端（店面）**：你在浏览器里看到的一切——登录页、政策列表、勾选框、Agent 运行进度、下载按钮。技术栈是 Vue 3 + Element Plus（一套现成的美观组件库）。

**后端（后厨）**：看不见的部分——验证你是谁（登录）、查询政策、调用 AI、生成 Word 文件。技术栈是 Django（Python 最流行的 Web 框架）+ DRF（让 Django 专门提供 API 接口的插件）。前后端之间用 HTTP 接口（JSON 格式）对话。

**数据库（仓库）**：所有数据的家——政策原文、用户账号、Agent 每一步的运行记录、生成的文件路径。用的是 MySQL 8。

> 为什么要分成三块？各司其职：改界面不用动数据，换数据库不用重写界面。这是所有现代 Web 系统的标准骨架。

## 3. 数据从哪来：采集（爬虫）

系统的"原料"来自 8 个政府网站的公开页面（财政部、商务部、外汇局、税务总局 + 广东/广州的地方部门）。

```
政府网站 ──定时爬虫──→ 清洗/去重/分类 ──→ 数据库
          (每天8点)     (失败不落库)      (每条带原文链接)
```

要点：

- **定时**：服务器可通过 cron 配置每天早上 8 点自动采集新政策，是否启用取决于具体部署环境
- **礼貌**：每抓一个页面等 1~3 秒，不给对方网站造成压力
- **去重**：同一条政策不会重复入库（按来源链接判断）
- **可追溯**：每条政策都保存原文链接、发布日期、采集时间——日报里的每句话都能查到出处
- **容错**：某个网站临时打不开（502）只影响那几条，重试 3 次后放弃，不影响其他站点

## 4. 系统的大脑：ReAct Agent

"Agent"（智能体）是本系统最有特色的部分。它不是一段写死的流程，而是**让大模型（DeepSeek）自己决定下一步做什么**的循环：

```
        ┌────────────────────────────────┐
        │                                │
        ▼                                │
   思考(Thought) → 选择工具(Action) → 执行 → 观察结果
        │                                │
        │   满意？──否──→ Critic 审查 → 必要时重新规划 ─┘
        │
       是
        ▼
   生成日报(terminate)
```

四个角色协作：

| 角色 | 职责 | 类比 |
|------|------|------|
| Actuator | 决定下一步调用哪个工具 | 干活的员工 |
| Critic | 每几步检查一次方向对不对 | 质检员 |
| Replanner | 被 Critic 指出问题后调整计划 | 项目经理 |
| Terminator | 判断任务完成、产出日报 | 验收人 |

它能用的工具（"手脚"）约 10 个：查中央/地方政策、清洗正文、生成摘要（调 DeepSeek）、生成 Word、检索历史相似日报（RAG）等。

**两个安全设计**：

1. **步数上限**（≤15 步）：模型"发疯"循环时自动止损
2. **人在回路**：遇到拿不准的问题（如"某条政策是否算重大变化？"），Agent 会暂停，在网页上弹出问题，等人回答后继续——AI 不替人做最终判断

**RAG（检索增强）**：Agent 生成摘要前，会先检索历史相似日报作为参考，让产出风格一致、不凭空编造。

   ▼                         ▼

## 6. 部署形态：三个容器

整个系统用 Docker 打包成 3 个容器（可以理解为 3 个独立的小电脑），在新加坡云服务器上运行：

```
用户 ──→ Nginx(前端容器) ──→ 静态页面直接返回
              │
              └──/api/──→ Django(后端容器) ──→ MySQL(数据库容器)
```

- **为什么有 Nginx**：它是"门卫+分流员"——网页文件它自己直接发（快），API 请求转交给后端，数据库端口只对内开放
- **为什么用容器**：在任何装了 Docker 的机器上，一条命令 `docker compose up -d` 就能把整套系统原样跑起来，不用逐台机器装环境
- **数据不丢**：数据库内容、Agent 生成的 Word 文件都放在"持久卷"里，容器删了重建数据还在

## 7. 安全与账号体系

- 登录采用 JWT（无状态令牌）：登录成功后发两张"门票"——短期票（2 小时）+ 长期票（7 天）。短期票过期时系统自动用长期票换新票，用户无感；长期票也过期才需要重新登录
- 每个 Agent 运行记录归属创建者，别人的记录看不见（跨用户访问返回"不存在"）
- 数据库和后端端口只绑定服务器本机回环地址，外部无法绕过 Nginx 直连

---

## 8. 质量保障

- **209 个自动化测试**，覆盖爬虫解析、Agent 状态机、API 权限、用户隔离等；CI 要求覆盖率 ≥80% 才允许合并
- **消融实验**：分别关闭 Critic/Replanner/停滞检测各跑一遍，用数据证明每个组件的贡献（如关 Critic 后成功率 75%→25%）
- **运行轨迹全记录**：Agent 每一步的思考、调用、结果都落库，网页上可回看——出问题能定位到具体步骤

## 9. 名词速查

| 术语 | 一句话解释 |
|------|-----------|
| 前端/后端 | 浏览器里跑的界面 / 服务器上跑的逻辑 |
| API | 前后端之间约定好的对话格式 |
| JWT | 登录后发的"通行证"，带在每次请求里证明身份 |
| Agent/智能体 | 能自主决定步骤、调用工具完成任务的 AI 程序 |
| ReAct | "推理+行动"循环：想一步、做一步、看结果再想 |
| RAG | 生成内容前先检索参考资料，减少编造 |
| Docker/容器 | 把程序和它的运行环境打包成标准箱，到处可跑 |
| Nginx | 高性能门卫：分流静态文件和 API 请求 |
| cron | Linux 的定时任务，本项目每天 8 点触发采集 |
| 消融实验 | 逐个关掉组件看指标变化，验证设计必要性 |
