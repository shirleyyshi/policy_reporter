## 1. 项目定位与叙事主线

### 1.1 一句话（简历项目标题下第一行）

> 基于 ReAct 范式的财税政策日报生成 Agent：Django + Vue 全栈实现政策采集、LLM 自主工具编排、Word 日报生成与全程轨迹可观测。

### 1.2 30 秒口头版（自我介绍里带过）

> 我做了一个政策日报 Agent 项目：后端定时从 8 个政府公开站点采集财税政策入库，用户选一个日期，Agent 用 ReAct 循环自主决定"取数—清洗—去重—分类—摘要—生成 Word"的处理顺序，每一步的推理和工具调用都落库可查。我给它配了 Critic 质量检查和消融实验，用来验证每个组件到底有没有贡献，而不是堆技术。

### 1.3 3 分钟完整版（STAR）

- **S 背景**：政策研究/合规岗位每天要人工浏览多个政府网站、筛政策、写日报，重复劳动且容易漏。
- **T 目标**：做一个可追溯、可观察的自动日报原型——重点不是模型多强，而是"LLM 在受控工具集内工作，人能审计它每一步做了什么"。
- **A 做法**：
  1. 数据层：requests + lxml 写配置化爬虫，8 个站点（4 中央 + 4 地方）XPath 全部收敛在 `crawl_config.json`，按 `source_url` 增量去重，带采集时间戳，零新增依赖。
  2. Agent 层：自研 ReAct 主循环（Actuator 每步一次 LLM 决策 / Critic 每 3 步质量检查 / Terminator 纯代码硬终止），10 个工具批量操作状态对象，LLM 只看计数摘要，控制 token。循环防护做了四层：最大步数、重复调用检测、连续失败终止、停滞检测。
  3. 可靠性：LLM 调用指数退避重试；状态每步落库（AgentRun），重启后可读取；人在回路用后台线程 + 前端 2 秒轮询 + 5 分钟超时兜底。
  4. 评估层：6 种数据场景自动发现（dense/sparse/empty/duplicate/partial_missing/with_legal），LLM-as-judge 三维打分，4 组消融实验验证组件贡献。
  5. 工程化：Docker Compose 三容器、gunicorn 多 worker、JWT、GitHub Actions CI（覆盖率门槛 80%）、约 185 个测试。
- **R 结果**：端到端跑通，166 条真实政策入库；消融显示关掉 Critic 后成功率从 75% 掉到 25%，且 Critic 必须配套 Replanner 才能把诊断转成修复——这是"组件不是越多越好"的量化证据。

### 1.4 叙事主线（贯穿所有回答）

央国企技术岗最看重的三个词：**可控、可追溯、可评估**。所有技术选择都往这个故事上靠：
- LLM 只做决策和摘要，清洗/去重/分类是确定性代码 → **可控**；
- 每步推理、工具输入输出、参数全部落 AgentTrace 表 → **可追溯**；
- 消融实验 + LLM-as-judge，不吹组件先进，只看数据 → **可评估**。

## 4. 高频问题话术

### 4.1 技术选型类

**Q：为什么用 ReAct，不用 Plan-and-Execute？**
> ReAct 每步都有 observation 反馈，模型可以基于工具实际返回调整下一步，trace 也更可解释；Plan-and-Execute 一旦计划失败要全盘重规划，对政策数据这种"取完数才知道密度"的场景不合适——事实上我的 sparse 场景就是因为看到 fetch 结果才知道要调 RAG 补充。

**Q：为什么不用 LangChain？**
> 自研主循环核心不到 400 行，我能精确控制每一步的 prompt、trace 落库和消融开关。LangChain 的抽象层对这个体量的项目是负资产：消融实验要求我精确关掉某一个组件，框架反而碍事。当然如果团队已经在用 LangChain/LangGraph，迁移成本也不高，因为我的工具层本来就是纯函数签名。

**Q：为什么人在回路用轮询不用 WebSocket？**
> Django Channels + Redis 是一整套新基础设施，为了一个弹窗引入不划算。2 秒轮询在交互上用户无感，换来了部署零新增组件。如果未来上了 Celery + Redis，人机同步顺手就能换成队列应答。

**Q：为什么分类工具不用 LLM？**
> 数据库里 `type` 字段已经是结构化分类，再调 LLM 是浪费 token 还引入不确定性。这个工具的存在本身就是项目的态度：并非每一步都需要 LLM，确定性的交给代码，LLM 只做它不可替代的决策和摘要。

**Q：爬虫为什么不用 Scrapy？**
> 政府站是纯 HTML，requests + lxml 零新增依赖就够；8 个站点的差异全部收敛在 JSON 配置里，换站点改配置不改代码。Scrapy + Splash 对这个场景是过度设计。

### 4.2 架构与可靠性类

**Q：多 worker 下状态怎么共享？人在回路怎么同步？**
> 状态是"内存 cache + DB"双层：AgentRun.state_json 每步落库，任何 worker 都能读；运行中的线程和 threading.Event 在单进程内，这是当前原型的明确边界。生产化方案：`_RUN_CACHE`/`_WAIT_EVENTS`/`_HUMAN_ANSWERS` 三个全局 dict 迁 Redis，Event 换 BLPOP 阻塞读，改动集中在 core.py 半天工作量。（追问细节见 INTERVIEW_PREP.md Q2）

**Q：DeepSeek 限流/挂了怎么办？**
> 所有 LLM 调用走 `_call_llm_with_retry`，3 次指数退避（1s/2s/4s）。重试仍失败会累计 fail_count，连续 3 次失败由 Terminator 硬终止，状态落库标记 failed——宁可失败可查，不要挂死烧钱。

**Q：Agent 会不会无限循环？**
> 四层防护：max_steps=15 硬上限；连续 3 次相同 tool+params 触发 Critic 介入；连续 3 次失败直接终止；连续 5 步状态摘要无变化触发停滞检测。ask_human 还有 3 次上限。这些全是代码层硬规则，不依赖模型自觉。

**Q：状态恢复后 datetime 之类的对象怎么办？**
> 序列化时 datetime 转 ISO 字符串存 JSONField；恢复时状态可读、trace 可回放，这是设计内的取舍——所以我说"重启后可读取"而不是"重启后续跑"，边界我很清楚。

**Q：多用户之间数据会互相看到吗？（D1 已实现，正面回答）**
> 不会。AgentRun 有 user 外键，所有 run 级端点（trace/回答/下载/列表）都做归属校验：跨用户访问返回 404 而不是 403——响应和"不存在"完全一致，不泄露 run 的存在性，这是防枚举的常规做法。历史数据用 nullable 外键兼容迁移，功能上线前的旧 run 对所有人不可见。

**Q：登录态过期怎么处理？（D3 已实现）**
> JWT 双令牌：access 2 小时 + refresh 7 天。前端 axios 拦截器在收到 401 时自动用 refresh 换新 access 并重放原请求，单飞设计保证并发请求只触发一次刷新；refresh 也失效才回登录页。用户视角就是 7 天内无感续期。

### 4.3 数据类

**Q：为什么地方政策是广东/广州，不是上海？★（必备）**
> 项目部署在新加坡云服务器，上海部分政府站点对海外 IP 访问受限，无法稳定采集，所以我选了从该服务器可稳定访问的广东/广州公开源，先保证数据和链路是真实的。采集层是纯配置驱动的：crawl_config.json 里换 URL 和 XPath 就能切换站点，代码零改动——这反而验证了采集层的可扩展性。之后如果换国内服务器，接入上海源就是一次配置替换加一轮 dry-run 验收的事。

**Q：消融数据量这么小，结论可信吗？**
> 如实说：166 条政策、4 配置 × 4 场景，撑不起统计显著性，我不往这个方向包装。消融的价值是验证组件设计的合理性——no_critic 成功率 75%→25% 这种量级的变化方向是明确的；后续扩数据会做多 seed 平均加方差。另外 Critic 温度是 0，确定性组件相关结论相对稳。

**Q：爬虫日期解析失败怎么办？**
> 支持四种日期格式加正文兜底正则；都失败时以当前时间入库并在文档里标注了这是需要人工抽检的妥协点。没有静默当成"今天的政策"去污染日报——这是采集原则。

**Q：去重怎么做的？**
> 两层：入库时按 source_url 精确去重（增量采集幂等）；Agent 工具链里按 URL + 标题相似度（SequenceMatcher 0.85 阈值）二次去重，应对同一条政策多站转载。

### 4.4 央国企特供类

> 内网部署五问（DeepSeek 换本地模型 / 多 worker / 达梦金仓 / 等保 2.0 / 消融可信度）的完整话术见 `INTERVIEW_PREP.md`，此处只列新增两问。

**Q：政策数据如果要分级/涉密怎么办？**
> 现在采集的都是公开政策，但如果落地到企业内部资讯，改造点是明确的：模型层换内网 vLLM 部署的 Qwen（只改 BASE_URL）；数据层给 Policy 加密级字段、导出按密级过滤；访问层上 RBAC 和操作审计。这三块在 INTERVIEW_PREP.md 里有具体到字段和工时的方案。

**Q：你的项目和市面上"LLM 套壳"项目区别在哪？**
> 三个可验证的差异：一是有消融实验，每个组件的贡献有数据；二是失败路径是设计出来的——empty 场景走 ask_human、duplicate 走 dedup、限流走重试，不同输入走出不同 trace，不是一条 prompt 走天下；三是全程可审计，每步推理和工具 IO 落库，这恰好是企业场景最需要的属性。

### 4.5 开放素质类

**Q：你觉得 Agent 落地最大的坑是什么？**
> 我在这个项目里踩过的两个：一是"组件堆砌"——Critic 单独开只增加 32% 耗时不提升质量，必须配套 Replanner 才有意义，所以不做实验根本不知道组件有没有用；二是"评估缺位"——没有 eval 框架之前，我改 prompt 全凭感觉，有了 LLM-as-judge 和固定场景集之后每次改动才有对照。

**Q：怎么防幻觉？**
> 架构层面的办法比 prompt 层面更可靠：摘要工具的输入限定为当天入库政策正文，LLM 没有编造的自由度；trace 全程可回查，摘要里每条结论都能对应到 source_url。承认剩余风险：LLM 仍可能过度概括，所以 judge 的 coverage 维度就是查这个的。
